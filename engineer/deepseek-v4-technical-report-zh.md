## 摘要

我们发布了 DeepSeek-V4 系列的预览版本，其中包括两个强大的混合专家（Mixture-of-Experts, MoE）语言模型，分别是：

- **DeepSeek-V4-Pro**，总参数量 1.6T，激活参数量 49B
- **DeepSeek-V4-Flash**，总参数量 284B，激活参数量 13B

二者都支持 **100 万 token 的上下文长度**。

DeepSeek-V4 系列在架构与优化方面包含若干关键升级：

1. **混合注意力架构（hybrid attention architecture）**，结合了 **Compressed Sparse Attention（CSA）** 与 **Heavily Compressed Attention（HCA）**，以提升长上下文场景下的效率。
2. **Manifold-Constrained Hyper-Connections（mHC）**，用于增强传统残差连接。
3. **Muon 优化器**，用于实现更快收敛与更强训练稳定性。

> **编者注 | CSA 是什么？**  
> CSA 可以理解为“先压缩、再稀疏选择”的长上下文注意力路线。它背后的问题意识来自 long-context LLM 的共同瓶颈，也就是标准 attention 的计算量和 KV cache 会随着序列长度迅速膨胀。与完全 dense attention 相比，CSA 往往试图只保留最重要的跨位置交互，同时对 KV 表示做压缩，因此属于“结构化稀疏 + 状态压缩”的折中路线。它的前世今生可以追溯到 sparse attention、segment/block attention、memory compression 和 retrieval-style attention 这些长期脉络。DeepSeek 在 V4 中把它进一步系统化，用于把百万上下文从“理论可做”推进到“工程上可常态提供”。

> **编者注 | HCA 是什么？**  
> HCA 可以理解为一种更激进的注意力压缩思路。相比 CSA，HCA 更强调把历史上下文以高度压缩的形式保留下来，从而显著降低长序列下的 KV 存储与计算成本。它背后的思想和早期的 memory compression、state summarization、compressed context representation 有连续性。简单说，HCA 不是假设“每个旧 token 都该被等精度保留”，而是假设模型可以把很长历史投影成更紧凑的可用记忆。这类思路对百万 token 级别上下文特别关键，因为真正限制部署的往往不是模型能不能读，而是显存和吞吐是否扛得住。

> **编者注 | mHC 是什么？**  
> mHC 全称 Manifold-Constrained Hyper-Connections，可以看作是对残差连接的一次结构升级。传统 residual 的优点是稳定、简单，但在超深网络里它的表达能力和信号传播形态未必总是理想。Hyper-Connections 这条线尝试把残差通路做得更“宽”更灵活，让层与层之间的信息交换不只是简单相加。mHC 则进一步在这个更强的连接映射上加入流形约束，核心目标是防止数值不稳定，同时保留更强表达力。它的“前世”是 residual connection、highway/skip 风格结构和近年的 hyper-connection 研究脉络，“今生”则是把这种思路推到超大模型稳定训练这个现实问题上。

> **编者注 | Muon 优化器是什么？**  
> Muon 是近两年受到关注的一类新优化器路线，目标是在大模型训练中同时改善收敛速度和稳定性。它并不是简单替换 AdamW 的一个小变体，而更像是在“参数更新几何”和“训练稳定性控制”上重新做平衡。过去几年里，大家已经逐渐意识到，超大模型的优化器不是无关紧要的底层零件，而是会显著影响可训练性、训练成本和最终性能的关键组件。DeepSeek 在 V4 中采用 Muon，说明他们不只是在改结构，也在尝试从优化动力学层面一起降本增效。

我们使用超过 **32T** 的多样化高质量 token 对两个模型进行预训练，随后通过一套完整的后训练流水线进一步激发并增强模型能力。

其中，**DeepSeek-V4-Pro-Max** 作为 DeepSeek-V4-Pro 的最高推理强度模式，在开源模型中重新定义了当前最优水平，在核心任务上超越了此前版本。

与此同时，DeepSeek-V4 系列在长上下文场景下具有很高效率。在 **100 万 token 上下文** 设置下，与 DeepSeek-V3.2 相比，**DeepSeek-V4-Pro** 仅需要：

- **27% 的单 token 推理 FLOPs**
- **10% 的 KV cache**

这使得我们能够常态化支持百万 token 上下文，也让长时程任务（long-horizon tasks）以及进一步的 test-time scaling 更具可行性。

## 1. 引言

推理模型（reasoning models）的出现（DeepSeek-AI, 2025; OpenAI, 2024c）确立了一种新的 **test-time scaling** 范式，并为大语言模型（LLMs）带来了显著的性能提升。

然而，这一扩展范式从根本上受限于传统注意力机制（vanilla attention mechanism）的 **二次计算复杂度**（Vaswani et al., 2017），这会在超长上下文与长程推理过程中形成难以承受的瓶颈。

与此同时，长时程场景与任务的出现，例如：

- 复杂的 agent 工作流
- 大规模跨文档分析

也使得对 **超长上下文的高效支持** 成为未来进展的关键。

尽管近年来已经提出许多面向长上下文的高效注意力变体，但它们常常在以下维度上存在明显权衡：

- 表达能力
- 训练稳定性
- 推理效率
- 工程可实现性

因此，真正困难的问题并不只是“把上下文拉长”，而是：

> 如何在维持模型能力与训练稳定性的同时，把超长上下文支持做成一个真正可大规模部署的系统能力。

在这项工作中，我们提出 **DeepSeek-V4**，目标是朝着 **高效百万 token 上下文智能** 进一步推进。

DeepSeek-V4 系列包含两个模型：

- **DeepSeek-V4-Pro**：总参数量 1.6T，激活参数量 49B
- **DeepSeek-V4-Flash**：总参数量 284B，激活参数量 13B

它们都支持 **100 万 token** 的上下文窗口。

为实现这一目标，我们从模型架构、训练优化和系统基础设施三个层面进行了联合设计。

具体来说，我们的关键改进包括：

### （1）混合注意力架构

我们提出一种混合注意力架构，将：
- **Compressed Sparse Attention（CSA）**
- **Heavily Compressed Attention（HCA）**

结合在一起，以同时兼顾：
- 长上下文效率
- 模型表达能力
- 可扩展性

### （2）Manifold-Constrained Hyper-Connections（mHC）

我们引入 **mHC** 来增强传统残差连接。其设计目标是改善深层网络中的信息流动和优化特性，同时尽量控制额外成本。

### （3）Muon 优化器

我们采用 **Muon optimizer**，以获得：
- 更快的收敛速度
- 更好的训练稳定性

在训练方面，我们使用超过 **32T** 的高质量多样化 token 对模型进行预训练，并通过一套系统化的后训练流水线进一步解锁能力。

实验结果表明，DeepSeek-V4 系列不仅在核心基准上表现强劲，而且在长上下文场景中展现出显著效率优势。

特别是在 **100 万 token** 上下文设置下，与 DeepSeek-V3.2 相比，**DeepSeek-V4-Pro** 的：

- 单 token 推理 FLOPs 降至 **27%**
- KV cache 降至 **10%**

这意味着百万 token 上下文不再只是“理论支持”，而成为一种可以常规提供的能力。

从更高层的角度看，这一点的意义在于：

- 它降低了长时程复杂任务的推理成本
- 它让更长链条的 test-time scaling 更实际
- 它使模型在 agent、跨文档分析和复杂工作流等场景中的可用性提升

## 2. 模型架构

本节介绍 DeepSeek-V4 的核心架构设计。整体上，DeepSeek-V4 延续了 DeepSeek-V3 的若干有效设计，同时引入了三个关键升级：

1. **Manifold-Constrained Hyper-Connections（mHC）**
2. **结合 CSA 与 HCA 的混合注意力**
3. **Muon 优化器**

这些设计共同服务于一个目标：

> 在维持强模型能力的同时，把长上下文能力推进到百万 token 规模，并保持训练与推理的高效率。

### 2.1 继承自 DeepSeek-V3 的设计

DeepSeek-V4 并不是从零开始重建的架构。它继承了 DeepSeek-V3 中已经被验证有效的一些设计思想，并在此基础上进一步演进。

从系统工程角度看，这种做法很合理，因为它允许研究工作把重点集中在：
- 真正限制长上下文扩展的瓶颈
- 对训练稳定性和效率影响最大的模块

而不是在所有部件上同时做大幅变动。

因此，DeepSeek-V4 的创新重点不在“彻底换一套 Transformer”，而在于：
- 对残差/连接结构进行强化
- 对注意力机制进行长上下文导向重构
- 对优化器和系统栈进行联合升级

### 2.2 Manifold-Constrained Hyper-Connections

DeepSeek-V4 系列如图 2 所示，引入了 **Manifold-Constrained Hyper-Connections（mHC）**（Xie et al., 2026），以增强相邻 Transformer block 之间的传统残差连接。与朴素的 Hyper-Connections（HC）（Zhu et al., 2025）相比，mHC 的核心思想是：

> 将残差映射约束到一个特定流形上，从而在保留模型表达能力的同时，增强跨层信号传播的稳定性。

本小节先简要介绍标准 HC，再说明 mHC 如何被设计出来以支持稳定训练。

#### 标准 Hyper-Connections

标准 HC 会把残差流（residual stream）的宽度扩展为原来的 `n_hc` 倍。具体来说，残差流的形状会从 `R^d` 扩展到 `R^(n_hc × d)`，其中 `d` 是实际层输入的隐藏维度。

记第 `l` 层之前的残差状态为：

`X_l = [x_(l,1); ...; x_(l,n_hc)]^T ∈ R^(n_hc × d)`

HC 在此基础上引入三个线性映射：
- 输入映射 `A_l ∈ R^(1 × n_hc)`
- 残差变换 `B_l ∈ R^(n_hc × n_hc)`
- 输出映射 `C_l ∈ R^(n_hc × 1)`

残差状态更新可写为：

`X_(l+1) = B_l X_l + C_l F_l(A_l X_l)`

其中，`F_l` 表示第 `l` 层，例如一个 MoE 层。它的输入输出仍然都是 `R^d`，因此尽管残差流被扩宽了，内部层本身的设计却无需随之改变。

HC 的好处在于，它把“残差流宽度”从“隐藏维度”里解耦出来，形成了一个新的扩展维度，而额外计算开销通常不大，因为 `n_hc` 往往远小于 `d`。

但作者指出，虽然 HC 有潜力提升模型性能，在多层堆叠后却常出现数值不稳定，这会妨碍其在更大模型中的扩展。

#### 流形约束的残差映射

mHC 的核心创新，是把残差映射矩阵 `B_l` 约束在 **双随机矩阵（doubly stochastic matrices）流形**，也就是 **Birkhoff polytope** 上：

`B_l ∈ M := { M ∈ R^(n×n) | M 1_n = 1_n, 1_n^T M = 1_n^T, M ≥ 0 }`

这个约束带来的关键好处是：

1. `B_l` 的谱范数 `||B_l||_2` 被限制在 1 以内，因此残差变换是 **non-expansive** 的，也就是不会在前向传播或反向传播中无控制地放大信号。
2. 双随机矩阵集合在乘法下保持封闭，因此在深层堆叠 mHC 时，稳定性更容易维持。
3. 输入变换 `A_l` 和输出变换 `C_l` 也会通过 Sigmoid 被约束为非负且有界，从而避免信号相互抵消。

换句话说，mHC 并不是单纯把残差路径做得更复杂，而是在“更强表达能力”和“训练可控性”之间做了一个结构化平衡。

#### 动态参数化

这三个线性映射的参数并不是静态常量，而是 **动态生成** 的。作者把它们分解为：
- 动态成分（依赖输入）
- 静态成分（不依赖输入）

给定输入 `X_l ∈ R^(n_hc × d)`，先将其展平并归一化：

`X̂_l = RMSNorm(vec(X_l)) ∈ R^(1 × n_hc d)`

然后类似传统 HC，先生成未经约束的原始参数 `Ã_l`、`B̃_l`、`C̃_l`，再通过后续约束把它们映射到满足稳定性要求的参数空间中。

从系统视角看，这种做法的意义在于：
- 残差连接不再只是固定通路，而是能随输入自适应变化
- 但这种变化又不会完全失控，因为它被流形约束包住了

因此，mHC 既是一种表达增强机制，也是一种稳定性工程。

因此，mHC 不应只被看成一个“小技巧”，而应被理解为：

**对深层模型内部信息通路的一次结构性重设计。**

### 2.3 结合 CSA 与 HCA 的混合注意力

DeepSeek-V4 的另一项核心改进，是提出结合 **CSA** 与 **HCA** 的混合注意力架构。

这是整篇报告中最关键的设计之一，因为它直接对应 DeepSeek-V4 的核心目标：

**让百万 token 上下文在计算和存储上都变得现实。**

#### 为什么必须改注意力

标准注意力机制的主要问题在于：
- 计算复杂度随序列长度二次增长
- KV cache 也会随着上下文变长而快速膨胀

当上下文窗口来到几十万甚至百万 token 时，这会变成压倒性的系统瓶颈。

因此，如果想认真支持百万上下文，就必须对注意力机制做体系级重构，而不是只在实现层面微调。

#### DeepSeek-V4 的策略

DeepSeek-V4 没有简单采用单一稀疏注意力，而是组合两种机制：

- **Compressed Sparse Attention（CSA）**
- **Heavily Compressed Attention（HCA）**

这种“混合”思路的潜台词是：

> 单一机制往往难以同时兼顾表达能力、效率与超长上下文可扩展性，所以需要让不同机制覆盖不同功能区间。

### 2.3.1 Compressed Sparse Attention（CSA）

CSA 可以从名字直观理解为：

- **Sparse Attention**：并不对所有 token 两两全连接计算注意力，而是利用某种稀疏模式，只保留关键连接。
- **Compressed**：不仅做稀疏化，还通过压缩进一步降低长上下文计算与存储成本。

这类方法的核心思想是：

> 在长上下文中，并不是所有 token 之间的交互都同样重要。只要保留最关键的信息路径，就有机会以远低于全注意力的代价，近似保留大部分有效能力。

CSA 的价值主要体现在：
- 降低长序列 attention 计算量
- 控制 KV cache 或中间表示开销
- 在长距离依赖仍较重要的情况下保持一定表达能力

### 2.3.2 Heavily Compressed Attention（HCA）

如果说 CSA 的重点是“稀疏化 + 压缩”，那么 HCA 则进一步强调：

**更激进的压缩。**

HCA 的存在说明作者并不满足于“比全注意力省一点”，而是希望在超长上下文场景中，把某些注意力路径的成本压到足够低，从而真正让百万 token 成本可控。

这通常意味着：
- 并非所有上下文都以同样精细的粒度保留
- 某些历史信息会以更压缩、更摘要化的方式参与后续计算

换句话说，HCA 对应的是一种更强的“记忆压缩”思路。

### 2.3.3 其他细节

除 CSA 与 HCA 的主体机制外，DeepSeek-V4 还包含若干配套细节设计，用于：
- 保持训练稳定
- 兼容大规模分布式训练
- 让推理系统能够高效管理超长上下文的状态

这些细节之所以重要，是因为长上下文模型的难点往往不只在一个公式，而在：

**模型、并行策略、kernel、cache 管理与训练框架之间是否能真正协同。**

### 2.3.4 效率讨论

作者特别强调效率讨论，说明这篇工作不是“提出一个概念上支持长上下文的结构”就结束，而是更在意：

- 真实推理 FLOPs 有多少下降
- KV cache 有多少压缩
- 百万上下文是否能成为常态能力，而不只是实验室演示

报告给出的关键结果是：

在 **100 万 token** 上下文设置下，相比 DeepSeek-V3.2，**DeepSeek-V4-Pro** 仅需：
- **27%** 的单 token 推理 FLOPs
- **10%** 的 KV cache

这两个数字非常关键，因为它们分别对应：
- **算力成本**
- **显存 / 内存成本**

而真正阻碍超长上下文落地的，正是这两项。

### 2.4 Muon 优化器

除了架构层创新，DeepSeek-V4 还采用了 **Muon optimizer**。

作者给出的核心结论是，Muon 能带来：
- 更快的收敛
- 更高的训练稳定性

在超大规模模型训练中，优化器往往不仅决定最终性能，还决定：
- 训练能否稳定跑完
- 学习率与超参数空间是否足够宽容
- 是否能在合理成本下达到目标质量

因此，Muon 在这篇工作里并不是一个孤立部件，而是与：
- mHC
- 混合注意力
- 大规模系统基础设施

一起构成 DeepSeek-V4 整体设计的一部分。

## 3. 通用基础设施

如果说前两章主要回答的是“模型结构上做了什么”，那么这一章回答的是另一个同样关键的问题：

> 这些设计怎样才能真正训练起来、跑起来，并且在工程上高效可复现？

DeepSeek-V4 并不把基础设施当作附属实现细节，而是把它视为模型能力的一部分。作者认为，要让超大规模 MoE、百万上下文、压缩注意力和新优化器真正落地，必须在训练与推理系统栈上同步优化。

具体来说，他们在基础设施层面做了以下几类工作：

1. 在专家并行中实现 **细粒度通信-计算重叠**  
2. 使用 **TileLang** 提升 kernel 开发效率与性能  
3. 提供 **batch-invariant 且 deterministic 的 kernel 库**  
4. 引入 **FP4 量化感知训练**  
5. 在训练框架中扩展 autograd、checkpointing 与上下文并行  
6. 在推理框架中设计异构 KV cache 与磁盘存储策略  

这些工作共同服务于一个目标：

**把“理论上成立的模型设计”变成“现实中可训练、可部署、可复现的系统”。**

### 3.1 专家并行中的细粒度通信-计算重叠

MoE 模型的一个核心工程难题是：
- token 路由会把不同 token 分发给不同专家
- 专家通常分布在不同设备上
- 因而会产生大量跨设备通信

如果通信和计算被串行执行，MoE 的理论算力优势很容易被网络开销吃掉。

DeepSeek-V4 的做法，是为 MoE 模块设计并实现 **单个融合 kernel（single fused kernel）**，尽量把：
- 计算
- 通信
- 内存访问

三者完全重叠起来。

这背后的思想很明确：

> 不应该把 MoE 看成“先路由，再传输，再算 expert”，而应尽量把整个过程融合成一条流水线。

这类细粒度 overlap 的意义非常大，因为在大规模专家并行里，性能瓶颈往往并不只是 FLOPs，而是：
- 通信等待
- 内存带宽
- kernel 启动开销
- pipeline 空转

因此，这一节本质上是在回答：

**如何让 MoE 的系统效率真正接近它的理论效率。**

### 3.2 基于 TileLang 的灵活高效 Kernel 开发

作者采用 **TileLang（Wang et al., 2026）** 作为 DSL（Domain-Specific Language），以平衡：
- 开发效率
- 运行时效率

这是一个很现实的取舍问题。对于大模型系统而言：
- 如果全都手写底层 kernel，性能可能最好，但开发太慢
- 如果完全依赖高层框架，开发舒服，但性能常常不够

TileLang 的角色，就是在两者之间搭桥。

> **编者注 | TileLang 是什么？**  
> TileLang 可以理解为一种面向高性能张量计算的 DSL。它的目标类似于让开发者以比 CUDA 更高层的方式描述 tile-based kernel 结构，同时仍保留足够多的底层性能控制能力。它背后的长期脉络包括 TVM、Triton、Halide 一类“用编译系统提升 kernel 开发生产力”的路线。对大模型公司来说，这种工具很有价值，因为真实 bottleneck 往往不止一个 kernel，系统里会反复出现需要快速迭代优化的算子。

对于 DeepSeek-V4 这种级别的系统，kernel 开发能力本身就是研究效率的一部分。因为模型设计一旦变化，底层 kernel 也必须能快速跟上，不然很多结构创新会卡死在工程实现上。

### 3.3 高性能、batch-invariant 且 deterministic 的 Kernel 库

作者还特别强调，他们提供了一套：
- 高性能
- **batch-invariant**
- **deterministic**

的 kernel 库，用于保证训练和推理阶段的 **bitwise reproducibility**。

这点非常值得注意。

很多人谈大模型系统时只盯吞吐，但在真正复杂的研发体系里，可复现性同样关键。因为如果 kernel 的数值行为会随着：
- batch size
- 调度顺序
- 并行策略

变化而变化，那么：
- debug 会变得很痛苦
- ablation 会不可靠
- 训练/推理结果难以严格对齐

因此，deterministic kernel 的价值不仅是“更严谨”，更是：

**让大规模实验能被可信地比较和复现。**

### 3.4 FP4 量化感知训练

DeepSeek-V4 在基础设施层面还引入了 **FP4 quantization-aware training**，主要用于：
- MoE expert 权重
- indexer QK path

以降低内存和计算开销。

这一步很重要，因为论文前面已经说到，长上下文的主要瓶颈不仅是计算，还有存储，尤其是 KV cache 和参数访问成本。

> **编者注 | FP4 QAT 是什么？**  
> FP4 指的是 4-bit floating point，一种比 FP8 更低精度的浮点表示。QAT（Quantization-Aware Training）则是在训练过程中显式考虑量化误差，让模型在训练时就适应低精度表示，而不是训练完再硬压缩。它的前世今生可以追溯到 INT8/INT4 量化、fake quant、低比特训练，以及近几年从“后训练量化”进一步走向“训练期联合适配”的路线。DeepSeek 把 FP4 用在专家权重和部分注意力路径上，说明他们是在认真从训练期就为未来推理效率做准备。

作者还提到，在现有硬件上，`FP4 × FP8` 运算的峰值 FLOPs 暂时和 `FP8 × FP8` 相同，但从理论上讲，未来硬件完全可以把它做得再高效约三分之一。

这意味着：
- 现在已经能省内存和部分系统成本
- 未来硬件一旦跟上，还会释放更大的吞吐红利

### 3.5 训练框架

作者在训练框架里做了若干重要扩展，目的都是围绕一个主题：

**如何让超长上下文、大规模 MoE 和新优化器一起稳定、高效地训练。**

#### 3.5.1 Muon 的高效实现

既然 DeepSeek-V4 采用了 Muon 优化器，那么训练框架就不能把它当作一个简单 plug-in。作者提到，他们针对 Muon 设计了 **hybrid ZeRO strategy** 来提升训练效率。

这说明优化器选择会反过来影响：
- 参数切分
- 状态同步
- 显存布局
- 分布式训练策略

换句话说，优化器不是一个孤立的数学公式，它会牵动整个训练系统。

#### 3.5.2 mHC 的低成本高内存效率实现

对于 mHC，作者提到使用了：
- **recomputation**
- **fused kernels**

来实现更具性价比且更省内存的方案。

这很符合前文对 mHC 的判断。它虽然增强了残差通路，但如果实现方式过于昂贵，就会失去工程意义。因此作者显然不满足于“mHC 能 work”，而是还要求：

- 额外成本足够小
- 显存压力可控
- 能嵌入大规模训练流水线

#### 3.5.3 面向长上下文注意力的上下文并行

作者使用 **two-stage contextual parallelism** 来管理压缩注意力。

这说明在百万上下文场景里，传统的数据并行 / 张量并行 / 流水并行已经不够，需要专门针对“超长上下文本身”去设计并行方式。

从系统角度看，这类 contextual parallelism 的本质是在回答：

> 当一个样本本身就长得离谱时，如何把它拆到多设备上处理，而又不让 attention 和 cache 管理失控？

这对长上下文模型是关键问题。

#### 3.5.4 用于灵活激活检查点的扩展自动微分

作者还扩展了 autograd 框架，引入 **tensor-level checkpointing**，从而实现更细粒度的重计算控制。

这说明他们并不满足于传统“按层 checkpoint”的粗粒度方式，而是进一步把内存-计算折中做细。

这类设计的目标通常是：
- 显存不足时，用更多重算换内存
- 但又尽量不多付无谓的计算成本

在百万上下文训练里，这种细粒度控制往往是必要的，而不是锦上添花。

### 3.6 推理框架

除了训练，作者也对推理框架进行了专门设计。

因为在长上下文模型里，推理系统的瓶颈往往更尖锐，尤其是：
- KV cache 规模
- 前缀共享复用
- 存储层级管理

作者为此设计了：
- **异构 KV cache 结构**
- **磁盘存储策略**

目的是实现 **高效 shared-prefix reuse**。

这非常符合真实生产需求。因为大量实际请求并不是完全独立的，它们常常共享：
- 很长的 system prompt
- 公共文档前缀
- 长对话历史前缀

如果不能有效复用这些前缀，百万上下文能力即使存在，成本也会很难接受。

#### 3.6.1 KV Cache 结构与管理

KV cache 本质上是 Transformer 推理时保存历史 key/value 的状态。上下文越长，KV cache 越大，这也是为什么 long-context inference 往往受显存/内存而不是纯算力限制。

作者提出异构 KV cache 结构，意味着不同部分的上下文状态可能会：
- 用不同精度表示
- 放在不同存储层级
- 使用不同压缩与复用策略

这不是一个小优化，而是长上下文推理系统里最核心的问题之一。

#### 3.6.2 磁盘上的 KV Cache 存储

作者进一步设计了 **on-disk KV cache storage**。

这说明他们已经在认真处理一个现实问题：

> 当上下文长到一定程度，仅靠显存甚至主存都可能不够，系统必须引入更分层的状态存储策略。

把部分 KV cache 落到磁盘，听起来会担心速度，但如果与：
- 共享前缀复用
- 异步预取
- 分层缓存

结合得好，它就可能成为支持超长上下文的重要手段。

从工程思想上讲，这和数据库、操作系统里的层级存储设计其实是同一类问题。

## 5. 后训练

DeepSeek-V4 的后训练流水线采用了一个 **两阶段范式**：

1. **独立培养领域专家（domain-specific experts）**
2. **通过 on-policy distillation 做统一模型整合**

作者认为，相比从一开始就追求“一个模型同时学好所有东西”，更有效的策略是：
- 先让模型在各个关键领域形成专长
- 再把这些专长蒸馏整合回一个统一模型中

这是一种很强的系统化训练哲学。

### 5.1 后训练流水线

#### 5.1.1 Specialist Training

作者会针对不同目标领域，分别训练专门的 expert model，例如：
- 数学
- 编码
- agent
- instruction following

流程上，基础模型会先在高质量、领域特定数据上做 **Supervised Fine-Tuning（SFT）**，建立初始能力；随后再使用 **Group Relative Policy Optimization（GRPO）** 做强化学习，以便让模型行为更符合该领域的成功标准。

换句话说，这一阶段的目标不是平均地“都学一点”，而是刻意把不同领域的能力都练成强项。

#### 5.1.2 On-Policy Distillation

在获得一组不同专长的专家模型后，作者再通过 **on-policy distillation** 训练一个统一模型。这里统一模型扮演 student，向多个 teacher 学习，并优化 **reverse KL loss**。

这一步的意义在于：
- 把多个领域专家的能力汇总进单模型
- 尽量保留各个 teacher 的强项
- 避免最终系统只能依赖一堆分散 specialist 共同服务

> **编者注 | On-Policy Distillation 是什么？**  
> 蒸馏（distillation）本身并不新，早就有 teacher-student 学习的传统。on-policy distillation 的关键点在于，student 学习的数据分布不是完全离线固定的，而会随着当前策略/采样过程动态变化，因此它和 RL、rollout、teacher scheduling 常常耦合更紧。它的“前世”是知识蒸馏与 imitation learning，“今生”则更像是大模型后训练里把多个专家能力合流的一种工程化手段。

### 5.2 RL 与 OPD 基础设施

作者专门讨论了 RL 与 OPD（On-Policy Distillation）所依赖的基础设施，说明他们不是把后训练当作“训几个 checkpoint”这么简单，而是把它视为一个大规模在线系统问题。

#### 5.2.1 FP4 量化集成

作者把 FP4 量化继续整合进 RL / OPD 流程里。这说明量化不是只为了最终部署，而是在训练和后训练阶段都参与整体成本优化。

#### 5.2.2 面向全词表 OPD 的高效教师调度

对于全词表蒸馏，teacher 调度本身就可能成为成本瓶颈。作者为此设计了更高效的 teacher scheduling。

这类问题本质上属于：
- 谁来当 teacher
- 何时调用哪个 teacher
- 如何控制蒸馏成本与收益比

#### 5.2.3 可抢占且容错的 Rollout 服务

RL 系统里 rollout 往往是脆弱环节，因为它涉及：
- 长链条采样
- 外部环境交互
- 分布式 worker
- 异步失败与恢复

因此作者强调 **preemptible** 和 **fault-tolerant**，说明他们把 RL 基础设施当作生产级系统在设计。

#### 5.2.4 面向百万上下文的可扩展 RL 框架

如果模型本身支持百万上下文，而 RL 框架吃不下长输入，那整体能力仍然落不了地。因此作者进一步把 RL 扩展到 long-context setting。

#### 5.2.5 面向 Agentic AI 的沙箱基础设施

Agent 类任务通常需要：
- 工具调用
- 文件系统交互
- 命令执行
- 环境状态隔离

所以作者还构建了 agentic AI 的 sandbox infrastructure。这意味着他们在后训练中并不只是做静态问答，而是在面向更真实的交互任务。

### 5.3 标准基准评测

作者在后训练后，对标准 benchmark 做了系统评测。

#### 5.3.1 评测设置

这一节会定义：
- 各 benchmark 的运行方式
- thinking budget / reasoning budget
- 是否使用不同模式（如 Pro-Max / Flash-Max）

#### 5.3.2 评测结果

根据前文总结，核心结论包括：
- **知识**：V4-Pro-Max 在 SimpleQA、Chinese-SimpleQA 等世界知识评测上明显超过主流开源模型，并缩小了与 Gemini-3.1-Pro 的差距
- **推理**：通过扩展 reasoning tokens，V4-Pro-Max 在标准推理 benchmark 上超过 GPT-5.2 和 Gemini-3.0-Pro，但仍略逊于 GPT-5.4 与 Gemini-3.1-Pro
- **Agent**：在公开基准上与领先开源模型大致同级，在内部评测上超过 Claude Sonnet 4.5，并接近 Opus 4.5
- **长上下文**：在 100 万 token 设置下，对合成任务和真实用例都表现强劲，甚至超过 Gemini-3.1-Pro 的学术 benchmark 表现
- **V4-Pro vs V4-Flash**：Flash 在知识任务上因参数规模较小而略弱，但在给足 thinking budget 时，推理任务可达到接近表现，并在成本上更具优势

## 6. 结论、局限性与未来方向

作者最后会总结 DeepSeek-V4 的主要贡献：
- 通过 CSA + HCA 显著提升百万上下文效率
- 通过 mHC 和 Muon 改善训练稳定性与收敛
- 通过系统级基础设施设计，使这些能力在训练与推理上都可落地
- 通过预训练与后训练联合设计，把能力拓展到知识、推理、长上下文与 agent 等多个维度

同时，这篇工作也隐含了若干未来方向：
- 更高效的长上下文注意力机制
- 更成熟的层级记忆和状态压缩方法
- 更适合超长上下文的 RL / agent 基础设施
- 针对未来硬件进一步释放 FP4 等低精度路线的潜力

从更高层看，DeepSeek-V4 的意义不只是“又一个更强模型”，而是：

**它试图证明，百万 token 上下文不该只是 showcase，而应该成为下一代大模型的常规能力。**
